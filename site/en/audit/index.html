How the web audit works

When and how it runs

  • The run starts automatically every day at about 05:20 UTC (06:20 CET) in GitHub Actions. It can also be started by hand.
  • Each address is checked from the outside with at most about 40 short requests, without logging in, identified as “cyberlage-audit” with a link to the notices.
  • The new run replaces the previous one. The page always shows the latest run with date and time (UTC).
  • If a run fails, the last state stays visible. After more than 3 days without a new run the seal turns grey.
  • If an address cannot be reached there is no result rather than false findings.
  • The operator is notified only when the result changes compared with the last run.
  • Rules, weights and limits change only with a new rules version (now 1.0). Every change is in the history of the source code.

Exceptions for pure redirects

  • cyberlage.com does not serve a page, it only redirects to cyberlage.org. It is checked with its own profile, “Redirect”.
  • Groups that need page content are left out: Content Security Policy, Third-party content, Content type and framing, Discoverability, Privacy headers, Legacy leftovers. They count neither good nor bad, and coverage stays at 100 %.
  • Instead, additional checks apply: a permanent redirect (301) to the target keeping path and query, the same for www, whether the target answers, and whether the domain explicitly accepts no mail (Null MX, RFC 7505).
  • All other checks (TLS, HSTS, DNSSEC, CAA, SPF, DMARC) apply unchanged and with the same weights.
  • The site cyberlage.org is checked separately and in full.

How it is calculated

  • Each check counts 1 (passed), ½ (note) or 0 (failed). Checks that do not apply are left out, checks not run lower the coverage.
  • A group’s value is the mean of its checks. The score is the weighted mean of the groups times 100.
  • If the group TLS or Redirects has the value 0, the score is capped at 59.
  • Without 90 % of the weight checked there is no score, only a partial value.

What the Dreier Web Seal is and is not

  • The seal shows the score, badge (gold, silver, bronze), address and date of the latest run. Without the date it means nothing.
  • It is not a certificate from an assessment body or an official quality mark, not an independent audit and not a penetration test. It does not say a site is secure, only that certain publicly measurable points are met.
  • Checks are made from the outside only, with open rules. Vulnerability scanning and attack tests are not part of it.
How the code audit works

When and how it runs

  • The run starts automatically every day at about 05:40 UTC in GitHub Actions. It can also be started by hand.
  • The tools run in fixed versions. If one is missing or returns nothing readable, the check is “not checked”: it counts neither good nor bad and lowers the coverage.
  • Without 90 % of the weight checked there is no score, only a partial value.
  • A single finding in secrets or workflows caps the score at 59.
  • Individual findings go only to the operator, privately; the public sees only score and numbers. A message is sent only when the result changes compared with the last run.
  • The new run replaces the previous one. After more than 3 days without a new run the seal turns grey.

What the Dreier Code Seal is and is not

  • The seal shows the state of an automatic run: score, badge (gold, silver, bronze), project and date.
  • It is not a security assessment, not a review by people and not a penetration test. A passed check only means the tool found nothing.
  • Maintainability is a rule of thumb (complexity, file length) and carries little weight.
